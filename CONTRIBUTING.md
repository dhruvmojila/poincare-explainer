# Contributing to poincare-explainer

Thanks for helping. This repository holds the interactive explainer of "LLM Orchestration with Geometry-Aware Memory" (IEEE ICBDML 2026) and the `poincare-ball` TypeScript library it is built on. Two rules keep it trustworthy: every number shown on the page is computed in the browser by `poincare-ball` (no hard-coded results), and the provenance text in the footer and the README stays as it is (a reference implementation written after the paper; the experimental system is not part of this repository).

The project is maintained by one person, so the rules below exist to keep review fast and predictable. Reading this file takes five minutes and saves a round-trip on almost every pull request.

## Before you start

- Every pull request answers exactly one issue. If there is no issue for what you want to change, open one first; for anything larger than a local fix, wait for a reply so the design is agreed before the work.
- To claim an issue, leave a comment. There is no assignment step. A claim lapses after 14 days without a draft pull request, and one open claim per person is enough.
- Read the issue's **Acceptance** line. That line is the definition of done; a pull request is reviewed against it and nothing else.

## Set up

Node 20.19 or newer (developed on Node 22) and npm.

```bash
git clone https://github.com/<you>/poincare-explainer && cd poincare-explainer
npm install                      # both workspaces: packages/poincare-ball and site/
npx playwright install chromium  # once, for the end-to-end checks
npm run dev                      # Vite dev server at http://localhost:5173
```

## Checks that must pass

Run these locally before opening a pull request; CI runs the same commands.

```bash
npm test            # vitest, packages/poincare-ball
npm run typecheck   # tsc for the library and the site
npm run build       # library (tsc) then site (vite) into site/dist
npm run e2e         # Playwright: no overlapping text at five viewports, no console errors (needs the build)
npm run verify      # all of the above plus the gzip budget (JS + CSS + HTML at most 250 kB, fonts excluded)
```

## Working on the page

- One persistent canvas draws every scene; a chapter is a `Scene` in `site/src/scenes/` plus its cards in `site/src/chapters.ts`. Keep new scenes inside the shared world and the shared colour tokens in `site/src/lib/draw.ts`.
- Everything must work at 360 px wide without horizontal scrolling and with `prefers-reduced-motion` on; the end-to-end script checks both.
- Keep the bundle inside the budget; measure with `npm run verify` before and after.

## What a good pull request looks like

- Scope: the linked issue, and only that. No reformatting of unrelated code, no drive-by renames, no new dependencies without an issue that agrees to them.
- Tests: at least one test that fails without your change and passes with it. Library changes: a vitest case in `packages/poincare-ball/test/`; if the public API changes, update the library README too. Page changes: the end-to-end run must stay green at every viewport, which is the overlap test.
- Docs: update the user-facing documentation when behaviour changes (chapter copy lives in `site/src/chapters.ts`, scenes in `site/src/scenes/`).
- Title in the imperative ("Add `--root` to the tree command"); fill in the pull request template; pull requests are squash-merged, so commit history inside the branch does not matter.

## Maintainer-only files

These are changed by the maintainer only, usually as part of a release. Pull requests that modify them are closed with a note; open an issue instead.

- `.github/` (workflows, templates, `CODEOWNERS`)
- `package.json` and `packages/poincare-ball/package.json` versions, `package-lock.json`
- `CITATION.cff`, `.zenodo.json`, `LICENSE`, `SECURITY.md`, `CODE_OF_CONDUCT.md`
- The citation chapter's bibliographic text, the footer provenance text and the README's provenance paragraph
- `docs/screenshots/` and `site/lighthouse/` (regenerated by the maintainer at release time)

## AI-assisted contributions

Using an AI tool to write code or text is fine. What is not fine is submitting output you have not run and do not understand. The pull request template asks whether AI assistance was used; answer it, and be ready to explain a design choice in your own words during review. Pull requests that restate the issue without a working change, or whose checks were never run, are closed without further review.

## Review and merge

- Workflows for pull requests from forks run after the maintainer approves them, so there may be a short delay before CI reports.
- All CI jobs must be green. The maintainer reviews within about a week and may ask for one round of changes.
- Merges are squash merges by the maintainer. You keep authorship of the commit and are credited in the release notes of the release that ships it.
