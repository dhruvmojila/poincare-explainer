LLM Orchestration with Geometry-Aware Memory

A controller that decomposes a query, an ensemble of language models that answers it, a synthesiser that fuses the answers, and in the middle a memory that keeps what the system knows in hyperbolic space, where hierarchies fit. Nine chapters, one disk, code you can run.

Flat memory forgets structure

Knowledge about a domain is a hierarchy: a few broad ideas, many specific ones. Here is an illustrative taxonomy of ~200 concepts (six domains, then areas, topics and leaves), the shape of the domain knowledge the paper's memory holds, drawn the usual way in the flat Euclidean plane.

Every ring of the drawing shares one circumference. Each level has about three times as many nodes as the one above, but the room for them grows only linearly, so the ~120 leaves end up a few pixels apart.

Radial tidy tree, Euclidean plane. Node colour encodes depth, teal (root) to brass (leaves). Hover a node for its label.

The same tree in the Poincaré disk

Every edge now has the same hyperbolic length τ (here τ = 1.1). The picture looks squeezed towards the rim only because we are looking at hyperbolic space through a Euclidean window; the node markers shrink with the metric. In the geometry itself, nothing is crowded.

Exponential room

A hyperbolic circle of radius r has circumference 2π sinh r, not 2π r. The rings are drawn at r = 1 … 4. A tree whose levels grow like bdepth needs exactly this kind of room, which is why it embeds with almost no distortion (Sarkar, 2011), and why the paper stores hierarchical domain knowledge in the Poincaré ball .

      Ancestors, descendants, depth

      Hover or tap a node. Its ancestors light up brass, its descendants teal, and the readout shows its distance from the origin. A query that lands near quadriceps can walk inward for context (lower limb, musculoskeletal) or outward for specifics (rectus femoris, vastus lateralis). This is the hierarchy-aware retrieval the paper describes: similarity that accounts for both semantic content and structural relationships.

      A free-text query has no depth of its own, and a point near the centre of the ball is close to everything. The reference implementation therefore measures semantic similarity on a reference shell (direction only) and applies depth and ancestry as explicit structure; that is how it realises the paper's retrieval. Chapter 05 lets you type such a query.

      Time-weighted memory

      Memories carry a timestamp. The paper's memory uses time-weighted embeddings: geometric proximity is multiplied by a recency weight, so at equal hyperbolic distance newer evidence wins. Each memory here is attached to the node it is about; its label shows its age in days.

      Twelve dated memories around the anatomy tree (teal notes and logs, brass facts); opacity is the recency weight.

      fig. 05 · twelve dated memories beside their nodes · opacity = weight

      Three ways to forget

      The reference implementation ships three curves: an exponential half-life , the Ebbinghaus curve , and a validity window that holds full weight then ramps to zero. Move time forward and watch the memories slide down the curve.

      Ask the memory

      Type a query. It is embedded by the same offline hashing embedder the reference implementation uses (word and character n-gram features, keyed BLAKE2b, 256 dimensions), as is every memory here: the 43 anatomy nodes and the twelve dated notes. Similarity is measured on the reference shell at the root depth, direction only; score = e−d · w(Δt) with the curve and time position set above, so a fresh clinical note outranks an older one at the same distance and, as it ages, durable facts climb back.

        Capability matching

        Each sub-task is matched against the capability profiles the ensemble maintains, which here means a specialist role: physiologist, biomechanist, strength coach, analyst. The memory enters twice. It tells the controller how deep each sub-task sits in the domain hierarchy, and it supplies the context the sub-task is answered against.

        The small disk is the memory; each sub-task's dot sits at its depth.

        Ensemble and throttling

        The ensemble is provider-agnostic. Each provider gets a capability profile, every response is normalised to one standard schema so the synthesiser never sees provider quirks, and requests are load-balanced across providers.

        Lanes for provider-a, provider-b and provider-c; particles are requests; traces show latency, length and density.

        fig. 07 · three provider lanes · particles are requests · traces: latency, length, density

        Throttling detection

        A provider under rate limiting rarely says so. The paper's detector watches three things instead: response patterns, computation time and information density. Here provider-b's latency climbs while its answers get shorter and thinner; each signal is standardised against the provider's own baseline and combined.

        latency z 0.0 · length z 0.0 · density z 0.0 · score 0.00

        throttling suspected · provider-b

        Amber marks the request at which the combined score crossed the threshold.

        fig. 07 · request 1 of 24 · detector threshold 1.6

        Failover

        Once flagged, the provider is taken out of rotation and its pending sub-tasks are reissued to the others; it is probed again later and readmitted when its signals return to baseline. No sub-task stalls, and the synthesiser downstream sees the same response schema either way.

        After the flag, request particles flow only to provider-a and provider-c.

        fig. 07 · request 1 of 24 · after the flag, particles reach provider-a and provider-c only

        Weights move the choice along the front

        The brass marker is R*, the feasible candidate with the largest J; it slides along the front when the weights change.

        Floors, uncertainty, refinement

        A candidate may trade objectives against each other but never fall below a floor εj on a constrained one; here coverage ≥ 0.5 and cost score ≥ 0.2, drawn as lines. Hollow dots violate a floor and can never be chosen, however the weights are set. The fused answer carries an uncertainty estimate; when it is high the controller sends the weakest sub-task back round the loop: iterative refinement.

        Build with it

        npm install poincare-ball

import { PoincareBall, sarkarLayout, regularTiling, makeDecay,
         shellDistance, hashingEmbed, indexTree } from 'poincare-ball';
const ball = new PoincareBall(1);
ball.distanceArcosh([0.3, 0.1], [-0.2, 0.5]);   // eq. (3)
sarkarLayout(tree, { tau: 1.1 });               // hierarchy → disk
regularTiling(7, 3, 4);                         // the hero tiling
makeDecay('half-life', 14)(ageDays);            // recency weight
hashingEmbed('knee flexion');                   // the offline embedder
shellDistance(query, memory, 1);                // direction only
